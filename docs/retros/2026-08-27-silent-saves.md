# Retro — v0.2.0, the silent-write milestone (2026-08-27)

**Scope:** PR #3 (v0.1.2, the dead "Add a day" button) and PR #4 (v0.2.0, every
write says so when it fails). One report — "I tried to add a day 4 but it
wouldn't let me" — and two different bugs behind it: the one that caused it, and
the one that made it hard to find.

## What went well

- **The report was reproduced before it was explained.** The first instinct was
  to read `PlanView.swift`, find the nested buttons, and call it. That would
  have been right, but it would have been a guess with a good story attached.
  Writing `PlanEditingUITests` first meant the diagnosis arrived as
  `XCTAssertTrue failed - adding a day should open it for editing` on the old
  code and a pass on the new one. The difference between "I believe this is the
  bug" and "this is the bug" is one test.

- **The fix removed code.** The dead button was a `Button` wrapping an
  `ActionRow` — itself a `Button` — with `.allowsHitTesting(false)` on the inner
  one to stop them fighting. The fix was to delete the wrapper and let the row
  own its action, which is what the identical "Add an exercise" one screen down
  had always done. The bug was the deviation, not the absence of a feature.

- **The `try?` sweep was done as one mechanism, not twenty-one edits.**
  `Model/Saving.swift` is the single place that decides what a failed write
  does; `saveOrReport("adding a day")` is the only thing the call sites say.
  Adding a twenty-second write costs a phrase.

## What was hard to understand

- **Nothing about the failure was observable, and that was invisible until
  someone tried to observe it.** The offer on the table was "let me try it again
  and you can watch the logs." There were no logs. The path emitted nothing, and
  the `context.save()` under it was `try?`, so even a real refusal would have
  been silent. The absence of an instrument does not announce itself — you only
  learn the thermometer is missing at the moment you reach for it.

- **A green test suite that ran nothing.** The first UI-test run reported
  `** TEST SUCCEEDED **` having executed zero tests, because
  `app/RathiFitness.xcodeproj` is generated by XcodeGen and gitignored, and the
  new file was not in it. A suite that passes vacuously is worse than a failing
  one: it is a failing one that lies. `xcodegen generate` is not optional after
  adding a file, and nothing said so.

- **`try?` reads as normal Swift.** Twenty-one of them, and none looks wrong in
  a diff. Nobody decided that a failed save should be invisible; it was copied
  from the first one and then from each other. This is the shape that a
  structural guard catches and a code review does not.

## Follow-ups landed in this milestone

- **A guard whose remedy was not runnable.** `changelog-archive` has told people
  to run `make changelog-archive` since the guards landed, and this repo had no
  `Makefile` — so the only way to satisfy it was to cut and paste the sections
  by hand. It went unnoticed because the guard first fires the day a second
  minor series opens, which is today. There is now a `Makefile` and
  `bin/changelog-archive`, and `make guards` / `make guards-test` / `make test`
  are real commands too.

- Every one of the 21 silent saves is named and reported.
- `guards.d/silent-saves.sh`, registered in `EXTRA` and therefore run by
  `guards.sh all` — which `guards.yml` runs on every PR, so it is binding rather
  than merely present. That distinction is the one RIA's own guards got wrong
  once, and it was checked here on purpose.
- `SavingTests` (9 cases), including one that reads every call site back out of
  the source and asserts the phrase completes "save failed while ___". A message
  that degrades to "saving" fails the build.

## Follow-ups blocked (and why)

- **Retrying a failed write.** The honest answer is that nobody has seen
  SwiftData refuse a write in this app, so there is no failure mode to design
  the retry against. Building one now would mean shipping error-handling code
  that has never handled an error — which is how the `try?` habit started.
  Reporting is the part that can be verified today, so reporting is what
  shipped.
- **A UI test for the banner.** Same root cause: the banner needs a real
  failure, and forcing one means a fault-injection seam in
  `Store.makeContainer`. Worth doing when there is a second reason to want that
  seam; a production hook that exists only for one test is a cost with no other
  payer.
