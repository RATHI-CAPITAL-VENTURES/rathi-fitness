# Retro — v0.9.0, time away (2026-09-05)

**Scope:** v0.9.0. A declarable trip, a snapshot schema bump, and two stale
tests that the bump exposed.

## What went well

- **It had already been decided.** v0.4.0 rejected a streak-with-a-week-off and
  wrote down the week-off half as the next thing to try, with its cost: a model,
  a snapshot field, a CLI read. Fifteen months of product argument were already
  in the repo, so this milestone spent none of them again — and the price was
  exactly as quoted.
- **The rule came from the person using it.** The offered options were
  majority-of-week, any-overlap, and pro-rating. The answer was better than all
  three: per week, and training while away is a *bonus that shows but does not
  score*. That last clause is the part no option contained.
- **The schema guard did its job.** Bumping 5 → 6 immediately failed the app,
  the CLI fixture and the docs into agreement, which is precisely what
  `snapshot-schema` exists to force.

## What was hard to understand

- **The band is empty when there are no sessions at all.** Seven of the new
  tests passed `[]` sessions and inspected a band that does not exist. That is
  correct behaviour — "nothing before your first workout counts" — and it makes
  every away-week test need an anchoring session in an untouched week.
- **A stale `__pycache__` faked a regression.** After deliberately breaking
  `cli/gym` to prove the new schema gate fires, restoring the file left 33
  failures behind; the module had been cached in its broken state. Two minutes
  spent doubting a correct file.
- **`time_away` has to be understood by the reader, not just carried.** The
  field is easy to add and useless if `gym` reports consistency without
  subtracting it, which is why the schema table row spells out what a reader
  must do rather than only what the field contains.

## Follow-ups landed in this milestone

**Four tests rotted the same way**, two of them in this milestone: a literal
restating something the code already knows. `testFinishingTheLadderHasNoNext` hardcoded 9,000,000 and
broke when the ladder grew; `test_the_supported_schema_is_the_one_the_app_writes`
hardcoded `5` and broke on every schema bump. Both "failures" were the test being
stale, and in both cases the tempting fix is to retype the number — which leaves
a test that can only ever agree with whoever edited it last.

Two more turned up the moment the schema moved: `SnapshotTests` pinned
`currentSchema == 5` as a deliberate "remember to bump the CLI" reminder, and
`AssistedTests` pinned the same number in a test about pull-up assists, which
has nothing to do with it.

All four now derive or relax: the ladder reads `Tally.milestones`; the CLI test
reads `currentSchema` out of the Swift; `SnapshotTests` keeps the meaningful
half (the encoded value equals the constant) and drops the literal, because the
reminder it existed for is now a real two-sided check in the guard and the CLI
suite; and `AssistedTests` asserts `>= 5`, which is the claim it was actually
making and stays true for ever.

**The habit worth keeping: when a test breaks after a deliberate change, ask
whether the assertion was ever a fact or just a copy of one.**
